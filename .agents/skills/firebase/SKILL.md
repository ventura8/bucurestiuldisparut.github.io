## Commands (inside the quality image)

```bash
docker run --rm -u "$(id -u):$(id -g)" -e HOME=/tmp/hcm-home -v "$PWD:$PWD" -w "$PWD" hcm-quality:local \
  bash -c 'mkdir -p $HOME && npx firebase emulators:exec --project demo-hcm --only auth,firestore,storage \
  "METADATA_SERVER_DETECTION=none npx vitest run --project functions --project functions-deps --project rules"'
docker run --rm -u "$(id -u):$(id -g)" -e HOME=/tmp/hcm-home -v "$PWD:$PWD" -w "$PWD" hcm-quality:local \
  bash -c 'mkdir -p $HOME && npm run build --workspace @hcm/functions'   # functions/dist, checked and loaded
```

The emulator JARs are baked into the image (`FIREBASE_EMULATORS_PATH`), JDK 21 included; `demo-hcm` needs no credentials. `.firebaserc`'s `default` is the real `bucurestiul-disparut`, so always name `--project demo-hcm`.

## Must know

- **The public viewer never reads Firestore** and loads no Firebase SDK for data; GA4 loads only after consent and only with a `measurementId`, never sees the URL hash, and has its cookies expired on withdrawal; Performance Monitoring is not in the public viewer (it would send the hash). Field measurements (Core Web Vitals through `web-vitals`, the apps' own timings: `docs/ARCHITECTURE.md` → *Field measurements*, `DECISIONS-for-review.md` §76) are GA4 events after consent too; `web-vitals` lives only in the lazy field chunks (`field-sdk.ts` of the engine and the admin), and every event passes the guard of `@hcm/shared` (`packages/shared/src/telemetry/`: each app's zod table, GA4's limits, no `?`/`#`/`@`, coordinate or tile path, a page budget) before `logEvent`.
- Functions: thin triggers call pure handlers through the ports of `functions/src/ports/`; Google APIs, Mapbox and USGS over REST with `fetch` so a fake `fetch` covers them; secrets read at runtime with a cache, never `defineSecret`; every writer validates with the shared zod schemas (`packages/shared/src/schemas/firestore.ts` for the content documents, `packages/shared/src/schemas/firestore-ops.ts` for the operational ones, paths in `packages/shared/src/schemas/paths.ts`). `firebase-functions-test` is not used: trigger tests call `.run(event)`.
- M2 contract (`docs/research/M2-interfaces.md`): every function is a row of the registry in `packages/shared/src/api/registry.ts` (access rule, App Check mode, instance cap, zod request and response); callables are built with `defineCallable` (`functions/src/api/callable.ts`) and fail with error codes (`ApiError` → `HttpsError(status, code, details)`, messages in `packages/shared/src/i18n/api/`). The fields a client may write are `CLIENT_WRITES` (`packages/shared/src/schemas/client-writes.ts`), mirrored by the rules.
- Wiring: `functions/src/index.ts` exports one group per namespace from its folder's factory; `functions/src/global-options.ts` sets `us-central1`, the caps and `runAs(name)`, the service account of every function (`fn-admin@` for callables and `ops.*`, `fn-events@` for triggers and the builder, `fn-crash@`, with no project role, for the public crash endpoint); `functions/src/deps.ts` builds `RuntimeConfig` and the adapters, and in the Functions emulator sends upstream calls only to the fakes at `HCM_UPSTREAM_BASE`, keeps secrets in their fake Secret Manager (each function runs in its own process; in memory without fakes), names the task queue's service account and enqueues manifest tasks without an id (the Cloud Tasks emulator dispatches at once). `functions/test/index.test.ts` checks the exports against the registry.
- Rules: default deny; admin is claim plus `admins/{uid}`; client writes exactly `CLIENT_WRITES` with the schemas' value checks and the stamp; no SVG; every `allow` tested allow and deny per persona; rule coverage evaluated true and false; a request may evaluate at most 1000 expressions, so checks stay cheap (bounded patterns, neutral defaults). A list the rules repeat from a shared constant (`validPushKinds` ← `NOTIFICATION_KINDS`) is pinned by a rules test that writes every value of the constant (`docs/LESSONS.md` 340).
- A collection-group rule matches that collection name everywhere: narrow `get` by the path (a path condition cannot hold for the collection-group query itself), and give every new server-owned field a value in the rules tests' complete document (`docs/LESSONS.md` 77, 78). Keep a collection-group query to its owner on the server, by a field the documents carry (`cityId` on history entries, the indexes starting with it), never by filtering in the page (lesson 149).
- A transaction re-checks every precondition it acts on, and a cap lives in a document it reads and writes (`ops/dispatch`), never in a query before it; the in-memory store runs transactions as they come, so a race test serialises them as Firestore would (`docs/LESSONS.md` 176, 177).
- Deploy artifact: `functions/build.mjs` writes `functions/dist/` with the lockfile of `functions/deploy-lock/` (stale lock: the build fails; refresh with `npm run deploy-lock --workspace @hcm/functions` in the pinned Node image, with the network) and one `.env.<project>` per project of `functions/deploy-env.json` (public `HCM_*` values only; a committed `.env.*` file is refused as a secret file). sharp is imported on the first photo, never at cold start.
- The Firebase web config, `.secret.local` and service-account files are never committed or opened by an agent.
- M4 (contract: `docs/research/M4-interfaces.md` §4, §5): a producer emits a notification by creating one `notificationEvents/{id}` document (`notificationEventId`: the same occurrence, the same id, so a redelivery writes nothing) through `documents`, never inside its own transaction; `notify.onEvent` fans it out to each admin's inbox and push devices. The assists' queue (`assist-geocode`, one Nominatim request a second) and the AI drafts' monthly cap (`usage/ai-YYYY-MM`, in a transaction) follow the M3 publisher's patterns; the three M4 ports (`Geocoder`, `Translator`, `PushSender`) are REST adapters in `Deps` like the others (`functions/src/adapters/{nominatim,vertex-ai,fcm}.ts`). Producers call `emitNotification` (`functions/src/api/notification-event.ts`). FCM: `firebase@13` deprecates `getToken`, so the admin registers with `register` and `onRegistered` and the server sends to the installation ID as `message.fid` (firebase-admin 14.5's `FidMessage`); a write that records something on an admin's own document (the item's `pushedAt`) reads it in a transaction, or it undoes what the admin did meanwhile (DECISIONS-for-review.md §54c, §54g).

- M6 Hosting (contract: `docs/research/M6-interfaces.md` §2): one Hosting site serves the public map at its root (the first city; other cities at `/<city>/`, any city made in the admin through the generic city page `/city/`) and the admin under `/admin/` (Vite base, `runtime.json` and `project.json` beside the page, the push worker's scope). `npm run build:hosting` (`scripts/site/src/hosting/`) assembles `dist/hosting/` (`hosting.public`; the start-up variant with `HCM_ADMIN_START_UP=1`) and the public `dist/hosting-public/`; `firebase.json`'s rules (redirects, a regex rewrite, `trailingSlash`) are resolved for the e2e by `scripts/site/src/admin/hosting.ts` in superstatic's order; the admin's CSP is a header on `/admin/**` only. A file a release changes under the same name (the legacy bundle's JSON) is `no-cache` and read with `cache: 'no-cache'`; only content that never changes under its name keeps a `max-age` (lesson 481). `adminUrl` is `https://<project>.web.app/admin/`; the viewer's token follows `viewerOrigins` through `ops.tick` (`functions/src/ops/viewer-tokens.ts`); a crash report's page decides its service.
- M6 installer (contract: `docs/research/M6-interfaces.md` §1, `docs/research/M6-status.md`): the admin installs the server (rules, indexes, functions with `--force` and retries of first-deploy races), the imagery pipeline and the public map through Cloud Build builds it submits with the owner's `cloud-platform` token as `hcm-installer@`, from the install bundle `npm run build:install` puts at `/admin/install/<slug>/`; D1 (the admin's first Hosting deploy) is the one terminal deploy left, ask first. Functions name their accounts in full (`<account>@<project>.iam.gserviceaccount.com`) for Cloud Scheduler; `ops.onProbe` backs the self-test's `events` check; the emulators skip IAM, so `roles/run.invoker` for the functions' accounts is proved only by that check on the real project. `HCM_VIEWER_ORIGINS` must match `httpsOriginSchema` (at most 10): `functions/build.mjs` and `runtimeConfig` refuse anything else, and a re-minted token the city cannot hold is deleted; `server.tgz` carries an allowlist of `functions/dist` (lessons 278, 279). The admin's Auth is `initializeAuth` with `browserSessionPersistence` (the viewer shares the origin; the popup's resolver goes with each popup). `firebase-tools` checks permissions of its own before a deploy, beyond those of the deploy's calls (`checkServiceAccountIam`: actAs on `<project>@appspot.gserviceaccount.com`; `checkHttpIam`; the trigger-region reads): lesson 298 lists them against the installer's roles, and the fake Cloud Build enforces the actAs check (finding 28 of 2026-10-31). `firebase-tools` loads the functions' source (`functions/dist`) to discover them, so outside a checkout their lock is installed there first: the server build's `packages` step (finding 30, lesson 300). A callable's response schema only gains optional or defaulted fields: an older server must still parse (lesson 297).

- M5 (contract: `docs/research/M5-interfaces.md` §1.2–§1.4): membership is `admins/{uid}.cities` (`owner` or `editor` per city; M13 adds two roles), written by the functions only; the rules read it with one `get` and close every city path, Storage prefix and export to the other cities' admins; every city callable checks the role in the request's `cityId` after validation (`requireCityRole`; access `cityEditor`, `cityOwner`, `projectOwner`). Prove isolation from outside too: another world's ID token on the emulators' REST (`S-A54-BAD-OTHER-CITY`).
- Findings 45 and 46 of 2026-11-01 (DECISIONS §79d–§79e, lessons 314–316): an event-delivered function never runs with one instance (a burst arrives while it starts and Cloud Run answers 429, each a Crashes group, though Pub/Sub redelivers): `ops.onBudget` has three of 80 requests, no minimum, and an idempotent handler. A refusal from an upstream keeps the upstream's own code to the admin and the log: `notify.registerDevice` refuses with `apiError.notify.deviceInvalid` and `reason` (FCM's `FcmError` code, its status, or `HTTP_<status>`), logged without the token; the admin then forgets the FCM SDK's IndexedDB record of the registration (trusted seven days whatever worker made it) and registers once more.
- Finding 50 of 2026-11-01 (DECISIONS §81d, lesson 322): a push device has `kind` (`token` | `fid`, `PUSH_TARGET_KINDS`; a device without one is an installation id), `notify.registerDevice` takes it (default `token`), and the FCM adapter addresses `message.token` or `message.fid` as it says (`PushTarget`). A dry run's `UNREGISTERED`/404 of the registration just made is recorded with a warning (never the token) and the first real send decides; `INVALID_ARGUMENT` still refuses. The fake FCM's `tokensInvalid`/`everyTokenInvalid` play a refusal the server keeps. The admin registers an FCM registration token (`getToken`, `deleteToken` on reset): firebase 13 marks both `@deprecated`, so `eslint.config.js` allows these two in `packages/admin/src/firebase/messaging-sdk.ts` only (the user's approval of 2026-11-01, `from: 'package', package: '@firebase/messaging'`); any other deprecated API stays an error, never an inline suppression. The FCM line above (`register`, `message.fid`) holds for the devices recorded before.

- M9 (`docs/research/M9-calibration.md` §2, §11): the approval policy needs `georef.method === 'auto'`, `georef.checkpointKind === 'held-out'`, a proof on record (`calibration.how` of `votes`, `pass`, `points` or `local-ai`, no `refusal`, no `checksDropped`, `measuredPct` at 70) and, on a USGS frame, `output.coveragePct` at 90 or more; a missing figure never approves, and `functions/test/imagery/approval-coverage.test.ts` holds it. `cities/{city}/imageryPasses/{key}` has no client rule: `imagery.onJobWrite` writes it (`pass-calibration.ts`) when `locate` ends proved, and `worker.step` reads only the scene's own mission and camera.
- M16 (contract: `docs/research/M16-recalibrate.md`): `imagery.recalibrate` (`cityEditor`, `fn-admin@`) starts a `regeoref` version carrying `recalibration` from a published version or one waiting for approval; a join answers `joinRecalibrate` (not calibrated again yet; the re-join is not built). A version with `recalibration` never publishes itself, and `imagery.approve` refuses one whose `recalibrationVerdict` is not `better`, or whose `basedOn` is not the layer's published version (`againstCurrent`), without `acceptWorse`. Refine and Snap leave a waiting base and its pending mark alone (`replaces`) until the new version is rendered: the approval policy's transaction replaces it then (only its own `basedOn` on the same layer; `recalibrate-replace.ts`), so a refine that declines changes nothing; the base records the refine (`refining`) so a second start is busy in the transaction, and a publish clears only its own pending mark. The worker adds only what it measured to `recalibration`, never `route`, `replaces` or `points`. `worker.step` accepts a run's `cancelled` without `cancelRequested` only on a `regeoref` with a decline's code (`isDeclinedCode`).
- M13 (contract: `docs/research/M13-roles.md`): `moderator` and `uploader` join `owner` and `editor` in `admins/{uid}.cities`. New roles are named where they are allowed, never subtracted: `isCityMember` and access `cityEditor` still mean owner or editor, `isCityReviewer` and `cityReviewer` add a moderator, `admin` access and `isStaff()` leave out an account whose every role is limited, and `member` is any admin document. `reviewStatus` is server-owned but for the `pending` an uploader's create must carry; `published` of a pending or refused item changes only through `review.decide`; a pending photo's derivatives are held in the private bucket (`review-held/`), so an uploader never gets a public address. `suggestions`, `contributors` and `roleRequests` have no client write rule. A rule that opens something to a new role needs its row in both directions in `firebase/rules-tests/test/roles.test.ts`. A trigger that acts on a rule's earlier answer decides again when it runs: `photos.onUpload` holds or refuses from the path's uid and the status as it stands (a refused photo never gets an address), an approval sends the `updatedAt` it saw (`apiError.review.changed`), and every cross-field refine of a schema (`aimedOnlyIfPlaced`) is in the create and the update rule alike. A suggestion keeps only what changes, and its decision records `undo`, so `suggestions.decide` with `revert` takes off exactly that decision.
- M17 (contract: `docs/research/M17-stories.md`): `cities/{city}/stories/{story}` is a place in every rule but its own `validStory` (title, a text of 10,000 characters per language, years, 20 photos, 20 places); `history.onStoryWrite` and `publish.onStoryWrite` join the families, `review.decide` and `history.revert` take `entity: 'story'` (a moderator reverts a photo, a place or a story); `review.decide` refuses to approve a story without text (`apiError.review.storyEmpty`): every check the editor makes before publishing is made again at the review door (lesson 444). The rules check a story's size only: its https links and figures are zod's (`storyDocSchema`) and the builder's. A new audited entity touches `HISTORY_ENTITIES`, `MANIFEST_ENTITIES`, `CLIENT_WRITES`, the registry, `global-options.ts`, the two trigger families and their tests (`on-write.test.ts`, `rebuild-manifest.test.ts`) in one change.
- M8 (contract: `docs/research/M8-join-interfaces.md`, as built §15): `imagery.join` (`cityEditor`, `fn-admin@`) creates everything in one transaction, reads first; `cities/{city}/imageryPlans/dates` is read by a city's members and written by no client, so its rule deploys with the admin that reads it, or the denied read makes the shell ask `admin.session` again. A frame a live join holds refuses `joinPartHeld`; `layers/delete.ts` reads the frame and its join itself, as `layers` may not import `imagery`.
- M7 (contract: `docs/research/M7-local-worker.md`, DECISIONS §83): the five `worker.*` callables (owner `fn-worker`, access `cityEditor`, App Check `off`: the only callables without it, each bound to the job the caller's worker claimed: `job.worker.{id,uid}` and no other live lease) and `imagery.runOn`; `worker.step` merges a write into the document and validates it with the shared schema plus the job's field and path allow-lists; `worker.urls` signs one object per URL for 15 minutes (PUT bound to its content type; the emulator's stand-in answers the Storage emulator's JSON API). `cities/{city}/workers/*` is read by the city's members and never written by a client. The dispatcher sets a job's `runOn` (the city's choice, `auto`: local while a worker was seen in three minutes), never sends a local job to Cloud Run, counts each cloud run into `usage/cloudrun-YYYY-MM` once (`usageCountedAt`) and holds a cloud run that would pass the free tier (`waitReason: 'free-tier'`, `job.needsOk` for automated jobs). The publisher takes Mapbox's Uploads API for a `studio.tif` of at most 300 MB within the month's 10,000 MB (`mapbox.via: 'uploads'`), MTS otherwise.
- Findings 65–69 of 2026-11-02 (DECISIONS §85, M7's addendum): pairing. `worker.pairCode` (admin) mints a one-time code into `cities/{city}/pairings/{sha256[:40]}` (no client rule; 10 minutes, the owner, the image digest); `worker.pair` (access `none`: no sign-in, App Check off; 20 attempts per city in 10 minutes in `pairings/limit`) exchanges it once for `auth.createCustomToken(uid, {worker: true, city, pair})` (fn-admin's own `signBlob`); `worker.revoke` (admin) revokes a worker and its pairing. Only rows with `workerToken` (the worker's five) admit a paired token, for its `city`, while the owner is a member and `paired` finds the pairing standing (`apiError.worker.revoked`); every other callable and every rule wants a Google sign-in. `worker.hello`/`worker.claim` compare the pairing's image with `setup/status.install.pipeline.image` (`outdated`: no job). `imagery.tick`'s `noWorker` marks a local job no computer came for in 15 minutes (`workerOverdueAt`, `job.noWorker`). `setup/status.provision.setVersion` records Provision's item-set version (`PROVISION_SET_VERSION`); `setup.recordCloud` keeps it when a report names none.
- Findings 59–72 of 2026-11-02 (DECISIONS §86, M7's addendum on the starter file and auto-pair): `worker.image` (no sign-in, App Check off, `fn-worker`, read-only) answers the installed pipeline image by digest for the starter file's supervisor (`apiError.notFound` while none); `worker.hello` takes the supervised worker's `image`, which `worker.hello` and `worker.claim` compare with the installed one (else the pairing's). `imagery.tick` backfills `usage/cloudrun-<month>` once (`backfilledAt`, `functions/src/imagery/cloud-usage-backfill.ts`); a later count keeps the mark. The admin's CSP `connect-src` names the local worker's `http://127.0.0.1:8765` and `http://localhost:8765` (the auto-pair; `scripts/site/src/admin/csp.ts` and `firebase.json` stay equal). A client that upgrades its server writes the server's new fields only after the new server is in place (lesson 350: Update the map records Provision's `setVersion` once the server build settled).
- Findings 73–74 of 2026-11-03 (DECISIONS §87, lessons 354–355): the installed pipeline image is what the job `raster-pipeline` runs (`functions/src/worker/installed-image.ts`: Run Admin `jobs.get` through `CloudRunJobs.job`, its `hcm-release` label's release, kept a minute per instance; the record `setup/status.install.pipeline` only when the job cannot be read, its release only for its own digest), the one answer of `worker.image`, `worker.hello`, `worker.claim` and `worker.pairCode` (`fn-admin@` holds `roles/run.viewer`, Provision set version 3). `worker.starter` is a public HTTPS function (`HTTP_ENDPOINTS`, GET and HEAD, `Content-Disposition: attachment`, CORS `*`) that fills the templates `functions/build.mjs` copies into `dist/starter/` (port `StarterTemplates`; the install bundle allows exactly those files).
- Finding of 2026-11-12 (lessons 558–560): a stored document its schema refuses (an older shape, a hand edit, a writer that skipped validation) must never lock its owner out. `setup/status` is read with `setupStatusReadSchema` (`packages/shared/src/schemas/legacy-reads.ts`: a malformed area reads as absent, the next write leaves it out) by every reader, server and admin; a version is ended (Reject, Cancel, the dispatcher's release) and listed with `layerVersionReadSchema` (the top-level fields it refuses left out, required fields still checked), and written back with the strict schema in its ended state. A tick part that loops over items catches every error per item (not only `ApiError`), logs the id and moves on.
- The city's tab icon (2026-11-08, `docs/research/M2-interfaces.md` → *The city's tab icon*): `cities.setIcon` (`cityEditor`, `fn-admin@`) takes PNG or WebP only, read from the bytes (`ImageProcessor.inspect`; a user's SVG never reaches sharp), and writes `cities/<city>/icon-{32,180,512}.png` in the public bucket under fixed names (five-minute cache) plus `cities/{city}.icon`, which no client rule allows. A public object a page links by a fixed name is overwritten in place, never content-hashed: the viewer cannot learn a hash without Firestore. `publish.buildManifest` draws the default first (`ensureCityIcon`, never failing the build); an icon-only write is not listed in the history (`UNLISTED_FIELDS`).

## Ask first, every time

`firebase deploy`, any `firebase`, `gcloud` or Firebase MCP action that changes a project, enabling an API, changing IAM or an org policy, accepting terms. The user runs `npx -y firebase-tools@15.34.2 login` themselves; agents never run `login:ci`, create tokens or type credentials.
