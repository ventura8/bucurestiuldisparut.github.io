# CI Pipeline

One script, one image, the same gates locally and in CI. This document is the overview: which gates apply to which file type, the CI workflows, tool versions and held dependencies. The **only** definition of the stages (and of `quality` and `all`) is [.agent/skills/quality/pipeline_skill.md](../.agent/skills/quality/pipeline_skill.md) → *Stages*; how to fix each gate is in [.agent/skills/quality/ci_quality_gates_skill.md](../.agent/skills/quality/ci_quality_gates_skill.md).

## How it runs

```bash
PIPELINE_STAGE=static bash scripts/ci/run-all-checks.sh   # or tests, build, e2e, sonar, deps, release, contract, quality, all (default)
python3 scripts/ci/pipeline.py --list                     # the live stage -> gate registry
```

1. `scripts/ci/run-all-checks.sh` builds `docker/Dockerfile.quality` as `hcm-quality:local` through `scripts/ci/build-and-test.sh` (seconds when cached).
2. It runs the image as the calling user, `HOME=/tmp/hcm-home`, the repository mounted at the **same absolute path** (coverage paths match Sonar's), nothing else from the host.
3. `scripts/ci/in-container.sh` refuses to run outside the image (`HCM_TEST_IMAGE=1`), then calls `python3 scripts/ci/pipeline.py --stage "$PIPELINE_STAGE"`.
4. `pipeline.py` runs `npm ci --prefer-offline` from the image's cache when the lockfile changed, then every gate of the stage, several at once (`scripts/ci/gate_runner.py`: at most `PIPELINE_JOBS`, by default the CPU count; a gate waits for the gates whose output it reads, Playwright runs alone) with each gate's output printed as one block in registry order, keeping going after a failure, and ends with `[SUCCESS] stage '<x>' passed` (writing `reports/pipeline/green-<x>.json` with HEAD and a hash of `git status`) or `[FAILURE] stage '<x>' failed: ...`.

Stages in one line each (the authoritative table is in the pipeline skill): `static` (every lint, format, type, architecture, secret and audit gate), `tests` (Vitest under the Firebase emulators, rule coverage, pytest, per-file coverage), `e2e` (the scenario registry check, the e2e site build, then Playwright behind the mock APIs: the admin tier under the emulators, the harness, the viewer smoke, the a11y specials, no-WebGL, the per-push layout and accessibility tour and the functional matrix: every scenario row), `tour-matrix` (the tour's other 35 viewport, theme and language projects), `build` (Vite with the engine's fonts, bundle budgets, the third-party notices, the GitHub Pages sites), `sonar` (the SonarScanner in the image, then the strict verdict; skipped with a notice, and passing, without `SONAR_TOKEN` or `.sonar-token`), `deps` (every pin on its latest stable release, weekly, never in `all`), `release` (on a tag: tag, versions, the released engine in `cdn/engine/` rebuilt byte for byte, the starter kit's pins, release notes, bundles and their notices, the CLI's package), `contract` (weekly: Setup Assistant deep links and third-party API shapes, never in `all`); `quality` is what CI runs, `all` (`quality` with `tour-matrix` after `e2e`, then `sonar`) is what runs locally before a push to `master` or a tag, and the nightly workflow runs `e2e` and `tour-matrix`. `bash scripts/ci/e2e-split.sh` runs any stage with its Playwright runs split between this machine and the NUC. A stage without gates would fail on purpose; since M0's leftovers closed (`docs/research/M0-handoff.md` §10f) every stage has its gates.

The registry holds 69 gates: `static` 52, `tests` 5 (`pytest` also runs in `static`), `e2e` 3 (`e2e-matrix` also runs in `static`; a run of `quality` or `all` runs such a gate once and reuses its outcome in the later stage), `tour-matrix` 3 (`e2e-matrix` and `e2e-build` reused), `build` 4, `sonar` 1, `deps` 1, `release` 7 (`kit-pins` also in `static`; `vite-build`, `bundle-budget` and `notices` also in `build`), `contract` 1.

- **Tiers**: `E2E_TIER` picks them (`e2e/projects.ts`); unset is every push's tiers, which carry every scenario row; `all` adds `tour-matrix`, which repeats the rows at the remaining combinations: the tour's other viewports, schemes and languages, the admin's tours in dark and English, the Setup journey and the imagery publishes (M3) at three more admin projects, the functional specs that do not depend on the window class at four more projects (the decisions: [research/DECISIONS-for-review.md](research/DECISIONS-for-review.md) §29a, §32d, §42g and §49k).
- **Machines**: the laptop (Intel Core i9-11900H, 8 cores and 16 threads, 30 GB) runs every stage; the NUC (`ssh nuc`, Intel Core Ultra 7 255H, 16 cores, 30 GB) runs only the head of each Playwright run of a split stage (the tour first) and four of the admin tier's six projects (four journeys; this machine runs `admin-l1440-ro` and the harness), in its own `hcm-quality:local` built from the same Dockerfile, from an rsync of the tree into `~/hcm-ci`. `HCM_SPLIT_PARTS=<here>:<NUC>` overrides the default shares of every tier but the admin tier; an unreachable or busy NUC runs the stage here only. The admin tier's tests run one at a time against a machine's own emulators, so a split gives each machine part of its projects (`E2E_ADMIN_PART`: `1-2/3` on the NUC, `3/3` here; `e2e/split.ts`) and slices the other tiers without counting them (`e2e/split-reporter.ts`): the two parts of that chain run at the same time ([research/DECISIONS-for-review.md](research/DECISIONS-for-review.md) §32f, §33a).
- **Gates at once**: every stage runs its gates side by side, up to `PIPELINE_JOBS` (default the CPU count); Playwright runs alone. ESLint lints on a quarter of the CPUs, at least two.
- **The image**: a dependency change rebuilds it for three to five minutes on each machine, and downloads (the npm packages, the Playwright browsers, the Firebase emulator JARs); an npm script edit, a release's version bump and a workspace whose dependencies are all workspaces do not (the `manifests` stage of `docker/Dockerfile.quality` drops the scripts, writes the workspaces' versions as 0.0.0 and leaves out the lockfile entries of a workspace it does not copy; [research/DECISIONS-for-review.md](research/DECISIONS-for-review.md) §31e, §63b). A machine whose BuildKit cache was evicted (the NUC builds other projects too) rebuilds it from scratch: the split's first run there downloads (§63g).

## CI workflows (`.github/workflows/`)

- `ci.yml` "CI Pipeline": push to `master` and `v*` tags, pull requests to `master` (drafts skipped), manual dispatch; concurrency per ref, cancelling superseded PR runs. Every push, tag and dispatch runs every job; a pull request whose every changed file is Markdown runs `static` only ([research/DECISIONS-for-review.md](research/DECISIONS-for-review.md) §28f).
  - `build-image` is the only writer of the GitHub Actions layer cache (scope `hcm-quality`): `bash scripts/ci/build-and-test.sh` with `HCM_DOCKER_BUILD_FLAGS` holding the `type=gha` cache flags. The local action `.github/actions/quality-image` frees runner disk, sets up Buildx and exposes the cache runtime to `docker build`.
  - `changes` ("Docs-only pull request?", `pull-requests: read`, seconds) lists a pull request's changed files with `gh api` (a rename's old path too) and outputs `docs-only=true` when every one ends in `.md`; on a push, a tag or a dispatch it outputs `false` at once. It runs on every event but a draft, because a skipped job would also skip `sonarqube` and the deploy jobs further down the chain. `tests`, `e2e` and `build` need it and run unless it says `true` (`if: !cancelled() && needs.build-image.result == 'success' && needs.changes.outputs.docs-only != 'true'`), so a failed listing, which leaves the output unset, runs them; on a docs-only pull request `sonarqube` is skipped with `tests`. No test, build or e2e input reads Markdown: every Markdown check (`markdownlint`, `agent-assets`, `skill-mirrors`, `editorconfig`, `gitleaks`) is in `static`.
  - `static`, `tests`, `e2e` and `build` need only `build-image` (the last three also `changes`) and run side by side, each `PIPELINE_STAGE=<stage> bash scripts/ci/run-all-checks.sh`, whose build loads the image from the cache; the deploy jobs need every one of them. `static` hands the commit range to the container (`GITLEAKS_LOG_OPTS` for `gitleaks-history`, `COMMIT_RANGE` for `commits`) and carries the type-checker caches from run to run with `actions/cache` (the `.tsbuild/` folders of `tsc -b` and `reports/.cache/mypy*`, which re-check whatever a change reaches; never an ESLint cache, whose type-aware verdicts a carried cache could keep stale); `tests` publishes the JUnit check "Unit Test Report", the coverage summary and the `coverage` artifact; `e2e` runs eight jobs split by tier and measured test time, each with its own `E2E_TIER` and `E2E_SHARD` from the matrix: the functional tier in three count shards, the per-push tour in three (every state runs the generic layout and accessibility checkers since 2026-10-17, and the admin's editor journeys joined it on 2026-10-18: about 4,150 s of test time in all, measured on the NUC in a split run), and the admin, smoke, a11y and no-WebGL tiers together in two (about 3,100 s); every tour and admin job starts the admin server and the Firebase emulators ([research/DECISIONS-for-review.md](research/DECISIONS-for-review.md) §33e, §37h; the measured times: [research/pipeline-baseline.md](research/pipeline-baseline.md)); `build` builds with the repository variable `MAPBOX_PUBLIC_TOKEN` (the URL-restricted `pk.` token, public by design) and uploads the bundles and, on `master`, the Pages artifact `dist/site/bucharest`. The timeouts are about two to three times each job's estimated run: `static` and `tests` 20 minutes, `e2e` 40, `build` 15.
  - `sonarqube` (after `tests`, so not on a docs-only pull request; not on fork PRs): the image, `scripts/ci/sonar_report.py --check-reports` in it (every report `sonar-project.properties` names), the scan and quality-gate actions, then the strict verdict of `scripts/ci/sonar_report.py`. Without `SONAR_TOKEN` or `sonar-project.properties` it ends with a notice instead of failing.
  - `deploy-pages`, `deploy-firebase` (rules, indexes, functions, admin Hosting with firebase-tools from the image) and `deploy-pipeline-image` (the Cloud Run Job image into Artifact Registry) are optional since M6, whose admin installs the server, the imagery pipeline and the public map itself through Cloud Build ([research/M6-interfaces.md](research/M6-interfaces.md) §2.8); they run only on a push to `master` with the repository variable `DEPLOY_ENABLED` set to `true` (M2), through Workload Identity Federation: variables `GCP_WIF_PROVIDER`, `GCP_DEPLOY_SA`, `GCP_PROJECT_ID`, `GCP_REGION`, environment `deploy`; no key. `deploy-firebase` installs (`npm ci`, every install script) before the authentication step writes its credentials file.
- `release.yml`: on `v*` tags, job `build` (read-only) runs `PIPELINE_STAGE=release`, shows the pinned jsDelivr addresses with their integrity in the job summary and uploads the bundles and the notes; job `publish`, the only one with `contents: write`, runs no repository code and creates the GitHub Release (title from the H1 of `docs/releases/vX.Y.Z_github_description.md`, that file as body, the engine and admin bundles attached) ([.agent/skills/quality/prepare_release_skill.md](../.agent/skills/quality/prepare_release_skill.md)).
- `nightly.yml` "Nightly E2E" (every day 02:37 UTC on `master`, and on demand): its own `build-image` (which also keeps the layer cache warm), then the `e2e` stage in the eight jobs of `ci.yml` and the `tour-matrix` stage, which `all` adds (the rest of the full tour: 11 viewports × light and dark × Romanian and English, the viewer's journeys and the admin's editor journeys, about 17,500 s of test time), in ten count shards (`E2E_SHARD` `1/10` to `10/10`, the largest frames first; the first about 2,000 to 2,400 s). Each part uploads its Playwright report and its log; when anything fails, the job `report` (`issues: write`, nothing but the local action) opens or updates the issue "Nightly e2e failed" through `.github/actions/upsert-issue`. With the local `all`, it is where the full tour runs; every push runs the per-push `tour` tier, which carries every tour scenario row ([research/DECISIONS-for-review.md](research/DECISIONS-for-review.md) §28).
- `deps.yml` (Mondays, `deps` stage) and `contract.yml` (Mondays, `contract` stage, no secrets): on failure the local action `.github/actions/upsert-issue` opens or updates one issue, "Dependency updates available" or "Third-party contract drift"; the issue quotes the gate's bullet lines (each pin that is behind, each stale hold). `deps.yml` opens it only when the log names such a line; a registry outage just fails the run.
- `codeql.yml`: CodeQL advanced setup (default setup stays off), `security-extended`, languages `actions`, `javascript-typescript`, `python`; on push, PR and weekly.
- Every action pinned by full commit SHA with a `# vX.Y.Z` comment; every job with `timeout-minutes`, least-privilege `permissions`, `persist-credentials: false`; runner `ubuntu-24.04` pinned; never `pull_request_target`; `${{ }}` values reach `run:` scripts through `env` (the last four are enforced by the `workflow-policy` gate). Editing workflows is ask first (`AGENTS.md` → *Boundaries*).
- Repository meta: `.github/pull_request_template.md` (the done checklist), `.github/ISSUE_TEMPLATE/` (bug and feature forms; blank issues off), `.coderabbit.yaml`, and the README badges in `.github/badges/` (written by the `coverage` gate; `unknown` until its first run).
