# Pipeline Skill

The single entry point for every quality check, locally and in CI, is `scripts/ci/run-all-checks.sh`. This file is the **only definition of the stages**; every other document links here instead of repeating the table. The gate registry itself is data in `scripts/ci/pipeline.py` (`GATES`, `STAGES`, `COMPOSITE_STAGES`), and `python3 scripts/ci/pipeline.py --list` prints it.

## How a run works

1. `scripts/ci/run-all-checks.sh` calls `scripts/ci/build-and-test.sh`, which builds `docker/Dockerfile.quality` as `hcm-quality:local` (override with `HCM_IMAGE`; extra `docker build` flags from `HCM_DOCKER_BUILD_FLAGS`). With unchanged manifests the build takes seconds.
2. It starts the image as the calling user (`--user $(id -u):$(id -g)`), with `HOME=/tmp/hcm-home`, the repository mounted at the **same absolute path** (so coverage paths match Sonar's) and nothing else from the host. It forwards, by name only (never a value in argv), `PIPELINE_STAGE` (default `all`), `CI`, `GITLEAKS_LOG_OPTS`, `COMMIT_RANGE`, `E2E_SHARD`, `E2E_TIER`, `MAPBOX_PUBLIC_TOKEN` (the site build's URL-restricted `pk.` token; unset means the e2e placeholder), `SONAR_TOKEN` and `PIPELINE_JOBS` (how many gates run at once; unset is the CPU count, `1` runs them one at a time).
3. Inside, `scripts/ci/in-container.sh` refuses to run unless `HCM_TEST_IMAGE=1` (set only by the image), then runs `python3 scripts/ci/pipeline.py --stage "$PIPELINE_STAGE"`.
4. `pipeline.py` first runs `npm ci --prefer-offline` from the npm cache baked into the image whenever `node_modules/.hcm-install-stamp` does not hold the SHA-256 of `package-lock.json` (delete the stamp to force it). Then it runs the gates of the stage several at once through `scripts/ci/gate_runner.py`: at most `PIPELINE_JOBS` (by default the CPUs the container may use; `1` runs them one at a time), a gate with `needs` starts after those gates of its stage finish (`coverage` after the test runners, `bundle-budget` and `site-build` after `vite-build`, Playwright after `e2e-build`), and an `exclusive` gate (`playwright`, `playwright-tour-matrix`) runs alone. The output stays a serial run's: each gate's output is one block in registry order, announced as `static 10/51 tsc` and closed by a line such as `tsc passed in 37.5s` (the gate's own run time), the earliest unfinished gate shown live; a stage ends with `static finished in 41.2s (gate time 163.0s, 51 gates, up to 16 at once)`. Every gate runs after a failure, so one run lists every problem, in registry order. Within one run of `quality` or `all`, a gate an earlier stage already ran on the same tree is not run again (`pytest` in `tests`, `e2e-matrix` in `e2e`, `e2e-matrix` and `e2e-build` in `tour-matrix`): its block ends `pytest passed in stage 'static' of this run (8.2s); not run again`, and a reused failure is listed under both stages.
5. The run ends with `[SUCCESS] stage '<x>' passed (reports/pipeline/green-<x>.json)` (exit 0) or `[FAILURE] stage '<x>' failed: <stage>/<gate>, ...` (exit 1). The green marker records `{stage, head, status_sha256}`, the hash of `git status --porcelain=v1 --untracked-files=all`, which the pre-push hook checks.

## Running it

```bash
mkdir -p reports/pipeline
PIPELINE_STAGE=static bash scripts/ci/run-all-checks.sh > reports/pipeline/run.log 2>&1; echo "EXIT=$?"
grep -E '^\[(SUCCESS|FAILURE)\]|FAILED' reports/pipeline/run.log
```

- Read the verdict from a log file; never pipe the run through `tail` (the pipe's exit status would be `tail`'s).
- **Two machines**: `PIPELINE_STAGE=<stage> bash scripts/ci/e2e-split.sh` runs the same stage with its Playwright runs split with the NUC (`HCM_SPLIT_HOST`, default `nuc`; `HCM_SPLIT_DIR`, default `hcm-ci`): the NUC gets the tree by rsync (what git sees, no ignored file) and runs the head of each Playwright run (the tour) and four of the five admin projects (`E2E_ADMIN_PART=1-2/3`) in its own image, this machine runs the whole stage with the tail (short functional tests) and the last admin project (`3/3`); the slices count every tier but the admin tier (`e2e/split-reporter.ts`), and each machine's admin part runs against its own emulators, at the same time as the other's. `HCM_SPLIT_PARTS` (`here:remote`) sets the shares; the defaults were measured on 2026-10-17 with this machine otherwise idle: `2:3` for `e2e` and `tour-matrix` (`E2E_SHARD=4-5/5` here, `1-3/5` on the NUC), `1:2` for `quality` and `all` (`3/3` here, `1-2/3` there; this machine runs `static`, `tests` and `build` besides). Measured before the tour's generic checkers: `e2e` in 306 s (275 s once the admin tier was split), `tour-matrix` in 133 s, `quality` in 324 s and `all` in 398 s, against 1052 s for `e2e` and about 1249 s for `quality` on the laptop alone before the optimisation; with them, `e2e` in 453 s and `E2E_TIER=all` (every tier, the full tour matrix included) in 19 minutes (2026-10-17, `docs/research/pipeline-baseline.md`). After the per-push tiering of `DECISIONS-for-review.md` §42g, `quality` in 460 s (2026-10-18), the two parts within about 20 s of each other. Output lines carry `[local]` or `[nuc]`; the single unprefixed `[SUCCESS] stage '<x>' passed` comes last, after the reports of both parts merge into `reports/junit/e2e*.xml` (the NUC's own in `reports/split/nuc/`). An unreachable, busy or tool-less NUC runs the stage here only, as `run-all-checks.sh`; a connection that drops mid-run has its part rerun here.
- Pick the stage by change: docs or tooling only → `static`; TypeScript or Python → `static`, `tests`, `build`; before a push to `master` or a tag → `all`.
- Never edit `scripts/ci/run-all-checks.sh` while a run is in flight: bash reads it by offset and the run dies with an unrelated error.
- `reports/` is git-ignored: `reports/pipeline/green-*.json`, `reports/coverage/ts/` (lcov, json-summary), `reports/coverage/{scripts,pipeline}.xml`, `reports/junit/{vitest,pytest,pipeline}.xml`, `reports/gitleaks.json`, `reports/sonar/scanner.log`.
- `sonar` runs after `tests` inside `all`; run alone with a token, it stops before any upload unless the `tests` reports exist. `deps` and `contract` need the network and fail on drift by design (they open the weekly issues).

## Adding a gate

1. Pin the tool: an exact npm devDependency, an exact line in `scripts/ci/requirements.txt` (plus its transitive pins), or a digest-pinned binary copied in `docker/Dockerfile.quality`.
2. Add `Gate("<name>", (...))` to `GATES` in `scripts/ci/pipeline.py`. npm tools get a `package.json` script and run as `(*NPM_RUN, "<script>")`, so `package.json` stays the one place for their flags.
3. Add the name to the right tuple in `STAGES`: cheapest first, network-bound gates (`npm-audit`, `pip-audit`) last. Gates run concurrently: a gate that reads another gate's output gets `needs=("<gate>",)` and is listed after it (the registry check refuses a need listed later), and a gate that saturates the machine or binds fixed ports gets `exclusive=True`. A gate must not write where another gate of its stage reads (the tools' caches live under `reports/.cache/`).
4. Run `python3 -m pytest` in the image: the registry tests reject unknown, duplicated or unstaged gates.
5. Update this file (*Stages*), `quality/ci_quality_gates_skill.md`, `docs/CI_PIPELINE.md` and the `quality-pipeline` skill and its mirror, in the same task.

## CI mapping (`.github/workflows/`)

- `ci.yml` (push to `master` and `v*` tags, pull requests to `master`, manual): `build-image` fills the GitHub Actions layer cache (`bash scripts/ci/build-and-test.sh` with `HCM_DOCKER_BUILD_FLAGS` set to the `type=gha` cache flags; the local composite action `.github/actions/quality-image` sets up Buildx and exposes the cache runtime). Every other job runs `PIPELINE_STAGE=<stage> bash scripts/ci/run-all-checks.sh`, whose own build loads the image from that cache; `static`, `tests`, `e2e` and `build` need only `build-image` (the last three also `changes`) and run side by side, and the deploy jobs need all of them: `changes` (seconds; `docs-only=true` when every file a pull request changes, a rename's old path included, ends in `.md`, then `tests`, `e2e` and `build` are skipped and with `tests` `sonarqube`; `false` at once on a push, a tag or a dispatch; a failed listing leaves the output unset and everything runs, `docs/research/DECISIONS-for-review.md` §28f), `static` (it exports the run's commit range as `GITLEAKS_LOG_OPTS` and `COMMIT_RANGE`, and carries the `tsc -b` and mypy caches between runs with `actions/cache`), `tests` (JUnit check, `coverage` artifact), `e2e` (eight jobs split by tier and measured test time, `E2E_TIER` and `E2E_SHARD` per matrix entry: `fn` in three count shards, `tour` in three, then `admin,smoke,a11y,nogl` in two; the tour and admin jobs start the admin server and the emulators; `DECISIONS-for-review.md` §33e, §37h), `build` (`MAPBOX_PUBLIC_TOKEN` from the repository variable of the same name, the URL-restricted `pk.` token; `dist` artifact; on `master` the Pages artifact `dist/site/bucharest`), then `sonarqube` (the image first, `scripts/ci/sonar_report.py --check-reports` in it, the scan and quality-gate actions, then the strict verdict of `scripts/ci/sonar_report.py`; skipped with a notice without `SONAR_TOKEN` or `sonar-project.properties`). The deploy jobs (`deploy-pages`, `deploy-firebase`, `deploy-pipeline-image`) run only on `master` with the repository variable `DEPLOY_ENABLED` set to `true` (M2), through Workload Identity Federation (`GCP_WIF_PROVIDER`, `GCP_DEPLOY_SA`, `GCP_PROJECT_ID`, `GCP_REGION`); `deploy-firebase` runs `npm ci` in the image before the authentication step, so no install script can read the short-lived credentials file.
- `nightly.yml` (daily 02:37 UTC, manual): its own `build-image`, then the `e2e` stage in the eight jobs of `ci.yml` and the `tour-matrix` stage (the rest of the full tour, as in `all`, the admin's editor journeys included) as `E2E_SHARD` `1/10` to `10/10`, each part uploading `reports/playwright*/` and `reports/test-results*/` (a `tour-matrix` run writes `reports/playwright-tour-matrix/`); a failure opens or updates the issue "Nightly e2e failed" (`.github/actions/upsert-issue`). Rebalance either matrix from the per-project times of `reports/junit/e2e.xml` when a tier grows; together the jobs must cover every tier.
- A job skipped in `ci.yml` also skips every later job whose `if` has no status function, all the way down the chain, even through a job that ran on `!cancelled()`: so `changes` runs on every event and answers `false` outside a pull request rather than being skipped, or `sonarqube` and the deploys would never run on `master`. A job that must run after a skipped or failed need carries `!cancelled()` and checks `needs.<job>.result` itself (`tests`, `e2e`, `build`). A docs-only skip is safe only while no test, build or e2e input reads Markdown: a test or build that starts reading a Markdown file makes `changes` count that file as code, or its check goes into `static`.
- Carried caches must re-check what a change reaches: `tsc -b`'s `.tsbuild/` folders and mypy's cache do (with restored caches a broken export of `packages/shared` still failed every dependent project, 2026-10-17); an ESLint cache does not, because with the type-aware rules a file whose imported types changed keeps its old verdict, so CI never carries one. Paths under `node_modules/` cannot be carried: the job's `npm ci` deletes them.
- `release.yml` (`v*` tags): job `build` (`contents: read`) runs `PIPELINE_STAGE=release` and uploads the bundles and the notes; job `publish` (`contents: write`, no checkout, no repository code) creates the GitHub Release with `docs/releases/vX.Y.Z_github_description.md` as body and the engine and admin bundles attached.
- `deps.yml` and `contract.yml` (weekly, Monday): `PIPELINE_STAGE=deps` / `contract`; on failure the local action `.github/actions/upsert-issue` opens or updates one issue ("Dependency updates available", "Third-party contract drift"). `deps.yml` opens it only when the log names a pin that is behind (` -> `) or a stale `HELD` entry; a registry outage just fails the run.
- `codeql.yml`: CodeQL advanced setup, `security-extended`, languages `actions`, `javascript-typescript`, `python`.

No workflow runs a lint or test tool itself. Every action is pinned by full SHA with a `# vX.Y.Z` comment (`action-pins`), every job has `timeout-minutes` (`workflow-timeouts`); every workflow has top-level least-privilege `permissions`, every checkout `persist-credentials: false`, no `pull_request_target` and no `${{ }}` inside a `run:` script (`workflow-policy`). The runner is `ubuntu-24.04`, pinned. Details: `docs/CI_PIPELINE.md`.

## Latest stable dependencies and holds

Every dependency stays on its latest stable release; a deliberate hold is a `HELD` entry with its reason in `scripts/ci/check_dependency_updates.py`, repeated in `docs/CI_PIPELINE.md` → *Held dependencies*. ## Local tooling quirks

- Never run a gate with the host's Node 22 or Python: versions differ from the image and results do not count.
- The GDAL base preloads tcmalloc; the quality image sets `LD_PRELOAD=""` because Chromium aborts under it. Keep it.
- A browser crash in the container writes `core.<pid>` into the repository root; `.gitignore` covers `core.[0-9]*`.
- npm 11 warns that `protobufjs` and `re2` (from `firebase-tools`) run install scripts not yet covered by `allowScripts`; approve those two explicitly if a later npm blocks them.
- pytest with `-c pipeline/pyproject.toml` makes `pipeline/` the rootdir and then ignores `testpaths`: the `pipeline-pytest` gate passes `--rootdir .`. `testpaths` is rootdir-relative, `pythonpath` relative to the config file.
- pytest 9's `caplog` captures records even from a logger with `propagate = False`; prove non-propagation with a handler on the root logger instead.
- `python3 -m venv` seeds pip 25.1.1 (12 advisories); a venv that Poetry fills is created `--without-pip`.
- ruff N802 also checks `.pyi` stubs: `ruff.toml` allows it for `pipeline/typings/**/*.pyi` only, so GDAL's CamelCase API is stubbed with ordinary positional-only `def`s under GDAL's names (`pipeline/typings/osgeo/`); the fake M2M server is a `wsgiref` app (no `do_POST`).
- Adding a workspace needs its `COPY <dir>/package.json <dir>/` line in the `manifests` stage of `docker/Dockerfile.quality` (and an allowlist line in `.dockerignore` outside `packages/*`), or `npm ci` fails in the image build.
- Prettier 3 prints `<!doctype html>` and self-closing void tags (`<meta ... />`), which html-validate's recommended `doctype-style` and `void-style` rules reject; `.htmlvalidate.json` therefore extends `html-validate:prettier`, which turns off exactly those rules (and `attr-quotes`), so a committed `.html` file can pass both gates. The site and admin pages still stay generated (decided 2026-10-12, `DECISIONS-for-review.md` §26): their meta CSP comes from each city's manifest and configuration and their Subresource Integrity from the pinned `mapbox-gl` release, so a committed copy would drift, and a template with placeholders would need a substitution step that is more code than `scripts/site/src/page.ts`. They are fully gated where they are made: the `tools` project checks every generated page against `.htmlvalidate.json` with the html-validate library (`scripts/site/test/page.test.ts`, `admin-page.test.ts`), and the e2e tier loads them behind the console guard. The harness pages are fulfilled by their specs (`e2e/specs/harness/`). The first committed `.html` file (the starter kit's template repository, M5) is linted by `htmlhint` and `html-validate` as is.
- Playwright answers a `page.route` before a `context.route`, and a later route before an earlier one: the firewall fixture is a context route registered first, so every mock wins over it.
- The quality image has a real `sonar-scanner` on `PATH` (`/usr/local/bin`). A test that removes its fake tool from its own `bin/` must also drop the image's directories from `PATH`, or the real tool runs (`scripts/ci/tests/test_sonar_scan.py` → `path_without_scanner`).
- `npm outdated --json --workspaces --include-workspace-root` prints `{}` with npm 11.19: the deps gate runs `npm outdated --json` (root) and `npm outdated --json --workspaces` separately. `npm outdated` exits 1 whenever something is outdated, so its JSON decides, not its status.
- GitHub's "latest release" of `github/codeql-action` is a `codeql-bundle-v2.x` bundle, not the action version: the deps gate reads `git/matching-refs/tags/v` (all `vX.Y.Z` tags, one request) instead.
- Prettier wraps an object entry longer than 140 columns after its key; for the i18n catalogues that breaks the one-line rule of the `i18n` gate. Keep messages short enough for one line.
- Node 24 strips TypeScript types natively, but our sources import `./x.js` and `@material/material-color-utilities` 0.4.0 imports without extensions: the JavaScript CLIs that load TypeScript (`scripts/seed/migrate-legacy.mjs`, `packages/ui/scripts/gen-theme.mjs`) register a `module.registerHooks` resolve hook that retries `.js` as `.ts` and appends `.js` to extensionless relative imports, then import dynamically. For the same reason the colour library is only reachable through the `@hcm/ui/dynamic-color` entry point: Vitest's node projects load npm dependencies with plain Node, and an engine or admin test that imported it through `@hcm/ui` failed with `Cannot find module …/dynamic_color`.
- `sonarjs/super-linear-regex` (ESLint) rejects patterns where two quantifiers can match the same text (`^\s*(\/?)\s*`); scan by hand with `indexOf` instead (`packages/shared/src/migration/html.ts`).
- Node 24 runs the site build and the e2e servers straight from TypeScript with `node --import ./scripts/site/register-ts.mjs <file>.ts` (a `.js` → `.ts` resolve hook); such files must use erasable syntax only (`erasableSyntaxOnly` in `scripts/site/tsconfig.json` and `e2e/tsconfig.json`).
- `sonarjs/code-eval` refuses `vm.runInNewContext`, so the site build reads `config.js` with the TypeScript parser (`scripts/site/src/config-js.ts`) and accepts one literal assignment only.
- A JSDoc comment that contains a glob with `**/` ends the comment at `*/`: write such globs in prose (Prettier then reports a parse error far from the cause).
- axe-core's CSSOM preload (for `css-orientation-lock`) writes `<style>` elements into a scratch document that inherits the page's CSP, so under the city sites' `style-src` it only logs violations: `e2e/support/a11y.ts` runs axe with `preload: false` and that rule off, passing the whole run options (`runOnly`, the disabled `rules`, `resultTypes`) through `AxeBuilder.options()`, which replaces whatever `withTags` or `disableRules` set before it.
- `AxeBuilder.analyze()` in its default mode injects axe-core (about 550 KB) into the page and every frame, runs it per frame, then opens a blank page, injects axe there too and merges the partial results in it: 0.4 s for one rule and 1.2 s for the tour's tags on an admin page whose own `axe.run` takes 0.11 and 0.16 s. A page of one frame (every page of the apps) therefore runs in legacy mode (`axe.run` in the page) on the first check of a document and through `page.evaluate` of the injected `axe.run` after that (`axeViolations`), with `resultTypes: ['violations']`; a page with frames keeps the default mode, which also tests cross-origin frames. A differential run of both ways over the tour, functional and a11y projects found no difference (`docs/research/pipeline-baseline.md` → *Addendum: the quality review*).
- A Playwright trace with DOM snapshots and screenshots records them at every action, and the tour's checkers are hundreds of actions per state (probes, Tab presses): `retain-on-failure` with both took 40 % of a tour project's test time and 20 % of a functional one's. `e2e/playwright.config.ts` keeps the trace of a failed test without them (its actions and timings, console, network, error) plus a screenshot and the error context; to see the DOM at each step, run the failing test again in the image with `--trace retain-on-failure`.
- Playwright's `getByRole` from a `role="dialog"` box does not find the dialog's slotted content (light-DOM children of the kit element): scope those queries to the element that renders the content.
- Playwright's default 30 s per test is too short for scenarios that walk several states of a SwiftShader map with eight pages in parallel: `e2e/projects.ts` gives the functional and a11y projects 60 s and the tour 240 s (its 3840 × 2160 frames, up to seven states per test through both generic checkers). With 8 workers the functional tier takes about seven minutes on the laptop and four on the NUC (measured 2026-10-17, `docs/research/pipeline-baseline.md`); the whole `e2e` stage (the `tour-matrix` tier aside) took about 10 minutes on the idle laptop alone, 5.5 on the NUC alone and 5 split between them before the tour's generic checkers, and 7.5 split since (453 s, every tour state through both checkers; `scripts/ci/e2e-split.sh`, 2026-10-17).
- Playwright 1.64 reads shard weights only from the environment variable `PWTEST_SHARD_WEIGHTS` (`8:1:3`, one weight per shard), and reads it after loading the config: `e2e/playwright.config.ts` turns an `E2E_SHARD` range (`2-3/3`) into that variable and a two- or three-part shard. A part is contiguous in the queue and counted in tests, not seconds. After a Playwright bump, check that two complementary ranges still list every test once (`npx playwright test --list` with `E2E_SHARD=1/3` and `2-3/3`).
- Projects that depend on another run in a later *phase*, and phases run one after the other: a dependency chain would serialise whole tiers. The admin tier stays one phase and serialises its tests with a Playwright test lock (`test.describe.configure({ lock })`), which the dispatcher skips past instead of letting a worker wait, unlike a blocking lease. Under full load the admin tests take about twice their idle time (the journey 20 to 30 s on the NUC before the state checks, 25 to 70 s with them), within their 90 s (300 s for the journey) timeouts.
- `playwright merge-reports` refuses blob reports recorded in different folders (the NUC's `~/hcm-ci` and the laptop's checkout): `scripts/ci/e2e-split.sh` merges with `--config playwright.config.ts`, which maps both onto this tree. The HTML report takes about 15 s more than the JUnit one, so a passing split merges JUnit only.
- At saturation, shorter waits do not buy throughput: with eight SwiftShader workers at 96 to 100 % CPU, `expect.poll` every 20 to 250 ms instead of Playwright's 100, 250, 500, 1000 ms changed the functional tier's test time by nothing measurable (1749 and 1649 s against 1664 and 1738 s on the NUC), because another worker uses the CPU a waiting one leaves. Waits are event-based where the page has an event (`waitForEngineEvent`, `mapIdle`: an in-page promise), and polls keep Playwright's intervals; the time goes to work, so cut work (tiers, a second machine), not waits.
- A dependency change rebuilds the quality image on every machine that runs a stage, the NUC included (three to five minutes each; 205 s on the laptop and 216 s on the NUC on 2026-10-17): `package-lock.json`, `.npmrc` or a `package.json` field other than `scripts` rebuilds from the `npm ci` and Playwright-browser layer on, `scripts/ci/requirements.txt` from the CI tools' venv on. An npm script edit does not (except `emulators:setup`, which that layer runs): the `manifests` stage of `docker/Dockerfile.quality` copies every manifest with its scripts dropped, and BuildKit keys the `COPY --from=manifests` on the copied content, so the image builds in about 2 s (before, 245 to 297 s; `DECISIONS-for-review.md` §32a). No manifest may gain an install lifecycle script (`preinstall`, `install`, `postinstall`, `prepare`) without moving it into that stage's kept scripts.
- Node's HTTP server closes an idle keep-alive connection after 5 s; a request Playwright's API client sends on it at that moment fails with `ECONNRESET` ("socket hang up"), which the e2e firewall reports as a blocked request. The mock APIs and the site server set `keepAliveTimeout = 0` (`e2e/mock-apis/server.ts`).
- Chromium logs every failed resource load as a console error, also a callable's by-design 401 or 400 and a Google 404 for a resource not created yet; the e2e console guard takes such errors only as `expectedConsoleErrors` (text and URL, with the reason) or claimed by the spec that causes them (`consoleErrors.takeMatching`).
- The Firebase Functions emulator: every function runs in its own worker process (no shared memory); a v2 scheduled function has the `http` signature, so a Pub/Sub publish to its `firebase-schedule-*` topic does not run it (the e2e world posts to its trigger route, `…/triggers/us-central1-ops-tick-0`, the `-0` being the emulator's trigger generation); the Cloud Tasks emulator ignores a task's delay; without `serviceAccountId` the Admin SDK asks the absent metadata server on every enqueue and waits about 14 s; a rebuilt `functions/dist` is not reloaded reliably, so restart the emulators after a functions build.
- A mock server reused across Playwright runs (`reuseExistingServer` outside CI) keeps each test's partition of the fake upstreams and the consent stand-in's records under the same test id: the admin tier resets both when a test starts.
- The type declarations of the Firebase SDK's Firestore module name `Temporal`; with `skipLibCheck` off the admin's tsconfigs add the `esnext.temporal` lib.
- `Intl.NumberFormat` puts a no-break space (U+00A0) between amount and currency in `ro-RO` (tests compare with `\u00a0`); Prettier reflows long Lit templates, so element tests trim `textContent`; Lit's `live` directive is a dependency Vite optimises on first use (a cold-cache reload, `DECISIONS-for-review.md` §14), so the admin avoids it; `Object.assign` copies a getter's value, so a test double of `document.cookie` needs `Object.defineProperty`.
- `git check-ignore --no-index` matches a folder pattern (`dist/`) only against a path it knows to be a folder: a build output that a fresh clone has not built yet (`functions/dist`, `packages/admin/dist`) is reported as not ignored, so the `agent-assets` gate failed on a clean checkout (the NUC, a new CI runner) and passed on a machine that had built once. `scripts/ci/check_agent_assets.py` asks about every missing path also in its folder form (`functions/dist/`).
- The tool caches the gates use, all git-ignored: `tsc -b` builds incrementally into the `.tsbuild/` folders, mypy and the pipeline's mypy keep `reports/.cache/mypy` and `reports/.cache/mypy-pipeline`, Prettier `reports/.cache/prettier/cache.json` and stylelint `reports/.cache/stylelint/` (both `--cache`, content strategy: a file is cached only when it passed, keyed on its content, the resolved config and the tool's version; stylelint 17 reports needless, invalid-scope and descriptionless disables while it lints a file, so such a file is never cached), ruff `.ruff_cache/`. ESLint has no cache on purpose: it keys a file on its own content, and the type-aware rules read other files' types, so a file whose imported types changed would keep a stale pass. It lints with worker threads instead: `--concurrency` a quarter of the CPUs and at least two (four here and on the NUC, two on a 4-vCPU runner). ESLint's own `auto` (half the CPUs) is slower beside the other gates, since each worker builds its own typed program: alone on the idle laptop four threads took 40 s, six 44 s, eight 58 s (2026-10-17); on the NUC eight took 27 s and four 34 s. Delete `reports/.cache/` to start cold.
- Gates of one stage run at the same time (`scripts/ci/gate_runner.py`), so `gitleaks dir .` walks the tree while other gates write: everything they write is git-ignored and under a path `.gitleaks.toml` allowlists (`reports/`, `.tsbuild/`, `node_modules/`, `.ruff_cache/`), and the image sets `PYTHONDONTWRITEBYTECODE=1`, so no `__pycache__` appears beside the sources. Keep new tool output there. `PIPELINE_JOBS=1` reproduces a one-at-a-time run when a gate behaves differently under load.
- A fixture file named `service-account.*.json` trips the repo policy's secret-file rule: name fake Google answers after their API (`cloud-storage/storage-agent.get.json`).
- The JVM prints `Picked up JAVA_TOOL_OPTIONS: ...` on stderr, and the Storage emulator relays it as `Unexpected rules runtime error` once at start-up: expected while `npm test` sets `-XX:CICompilerCount=2`. On 16 hardware threads the JVM's ergonomics start 12 JIT compiler threads (3 on a 4-vCPU runner), whose C2 work was about two thirds of the Firestore emulator's CPU in a run this short; C1 alone (`-XX:TieredStopAtLevel=1`) cut more but made the 250 MB rule-coverage reports slower to build than the tests gained.
- The Firestore emulator's rule-coverage report is about 250 MB of indented JSON (every distinct value of every expression, with its count), and its HTML embeds the same data; building either takes the emulator 3 to 8 s, so `check_rules_coverage.py save` asks for both at once.
- pytest-xdist with one worker per core (`-n auto`, 16 here) runs the CI tooling tests slower than four workers (7.8 s against 5.9 s): each worker imports and collects the whole suite. `pytest.ini` caps it at four; `-n 0` gives one process. The pipeline's tests stay in one process: each worker would import GDAL (9.2 s against 5.4 s).
- The floor of a split `e2e` run used to be the admin chain: its 22 tests run one at a time and sat at the head of the queue, so they all landed in the NUC's part and ended it. Since 2026-10-17 each machine runs part of the admin projects against its own emulators (`E2E_ADMIN_PART`, `1-2/3` on the NUC and `3/3` here, the NUC being about twice as fast; `DECISIONS-for-review.md` §32f, §33a); Playwright's own shard would count those tests and move the other tiers' boundaries differently on each machine, so `e2e/split-reporter.ts` takes over the slicing (`Reporter.preprocess`: `skipSharding()`, then `exclude()` of the other tiers' tests outside the range).
- rsync with `--filter=':- .gitignore'` (`scripts/ci/e2e-split.sh`, the session's NUC helper) copies a folder whose own `.gitignore` holds `*` as an empty folder without that file. In such a copy Hypothesis found `.hypothesis/` already there, wrote no `.gitignore` into it, and its cache files failed the `editorconfig` gate of the next `static` (`docs/LESSONS.md` #52); the root `.gitignore` now names `.hypothesis/`.
