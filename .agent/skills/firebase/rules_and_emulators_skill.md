# Rules and Emulators Skill

Firestore and Storage security rules, their tests, and the Firebase emulators every test tier uses. Rules outline: `docs/research/design-review-security-cost.md` §1.4–§1.5; tests: `docs/research/design-review-testability.md` §3.5; the M2 model the rules mirror: `docs/research/M2-interfaces.md` §2 (and CR-M2-28, what the rules enforce beyond `CLIENT_WRITES`).

## Projects

- Production: Firebase project `bucurestiul-disparut` (created with the user's yes; Spark until the admin links billing in-app). Its web config is never committed. `.firebaserc`: `default` is this project, `e2e` is `demo-hcm`.
- Tests: the **`demo-hcm`** project. The `demo-` prefix guarantees no real resource is touched and no credential is needed. Because the default project is real, **every emulator command names `--project demo-hcm`** (`firebase/rules-tests/test/firebase-config.test.ts` fails when an npm script starts the emulators without it).

## Rules (`firebase/`, M2)

- **`firebase.json` and `.firebaserc` live at the repository root**: firebase-tools refuses any path outside the directory that holds `firebase.json`, so from `firebase/` it could deploy neither `functions/dist/` nor `packages/admin/dist/`. The rules, indexes and rules tests stay in `firebase/`. Hosting deploys the site `bucurestiul-disparut` with the admin's security headers (`docs/ARCHITECTURE.md` → *Deployment configuration*).
- **Default deny**: `match /{d=**} { allow read, write: if false; }`; everything the M2 model does not name is denied.
- **Admin** = a verified Google sign-in (`email_verified`, provider `google.com`) with the custom claim `admin == true` **and** an `admins/{uid}` document (immediate revocation; a claim alone stays valid for up to an hour). A signed-in Google account reads only its own `admins/{uid}`.
- **The public never reads Firestore**: every collection is admin-only; the public reads only the static manifest and photo files in the public bucket.
- **Read-only for admins**: `setup/*` (status and owner), `invites`, `usage`, `ops`, `manifests`, job logs and every `history` subcollection (under `cities/{city}` and under each layer, photo, POI and POI category).
- **Client writes** follow **`CLIENT_WRITES`** (`packages/shared/src/schemas/client-writes.ts`) exactly: per collection, the fields a create may contain and an update may change, with the value checks of the zod schemas (`packages/shared/src/schemas/firestore.ts`, `firestore-ops.ts`) and the stamp (`updatedBy == request.auth.uid`, `updatedAt == request.time`). The rules tests import it, so a schema change fails them until the rules follow. Jobs can only be created (`queued`) or cancelled (not when `succeeded`, `failed` or `cancelled`); a scene's `status` becomes `candidate`, `ordered` or `rejected` only.
- Beyond `CLIENT_WRITES` (CR-M2-28): photo, POI, category and job ids follow `ID_PATTERN`, and no category is called `photos`; a photo's location lies within the city bounds ± 0.5° (checked on create and when it changes); publishing a photo or changing its licence needs `processing: 'done'`, an `image` and a licence other than `unknown`; required titles (`title.ro`, `name.ro`, `label.ro`) are refused blank, but an optional text that is blank and not empty passes the rules and is refused by the server's zod read, so the admin validates with the shared schemas before every write; geometries are checked by size, first vertex and ring closure, every link is checked.
- **The 1000-expression limit**: Firestore denies a request whose rules evaluate more than 1000 expressions, and every reference to a function argument evaluates the argument again (about ten per check). So a text is one bounded pattern (`[\s\S]{1,200}`, chained blocks above 1000 characters), an optional field is checked against a neutral default (`data.get('bearing', 0)`), and the whole document is validated on every write. The heaviest legitimate writes (a photo with every field and five links, every editable field of a city at once) use about 650 of 1000; `limits.test.ts` fails when one goes over. The emulator's `firestore-debug.log` names the limit when a write is denied for it.
- **Indexes** (`firebase/firestore.indexes.json`): photos by `published`, `processing`, `license` or `rightsReview`, then `updatedAt` descending; POIs by `category` or `published`, then `updatedAt` descending; layers by `published`, then `order`; jobs by `status`, then `createdAt` (both directions); history by `action`, then `updatedAt` descending; single-field exemptions for large fields (`previous`, `geometry`, `theme`). A history is listed by `updatedAt desc`: the emulator refuses descending scans on the document id (`orderBy('__name__', 'desc')`).
- **`gcps`** is not in the M2 model and is denied; M3 adds it back with a schema.
- **Many cities (M5, `docs/research/M5-interfaces.md` §1.4)**: a city path needs a role in that city, read with one `get` of `admins/{uid}.cities` (`isCityMember(city)`; `isProjectOwner()` for the project's own paths), never from the token, so a removal takes effect at once; `admins/*` is its own reader's or the project owner's, invitations the project owner's; History's collection-group list only with `where('cityId', '==', <a city of the admin>)`; `cities/{city}.limits`, `cities/{city}/usage/*` and `cities/{city}/exports/*` are read by the city's members and written by nobody (the functions only). Storage: a city's uploads, originals, photos, rasters, work and reference files per city prefix, the USGS browse copies any admin's, the private `exports/` nobody's (the signed address is the way out). The matrix tests every persona against city B as a member of city A (`outsider`, `<scope>-elsewhere`); the exports' row is `S-A53-BAD-CLIENT-EXPORTS` in `cities.test.ts`, its own `describe` (a `describe` callback is a function too: 120 lines at most).
- Storage: the private bucket accepts an admin's upload only into their own folder under an existing photo document, `uploads/photos/{city}/{uid}/{photo}/{file}` (`file` matches `UPLOAD_FILE_PATTERN`, 1 byte to 60 MiB, JPEG, PNG, WebP, TIFF or HEIC/HEIF, `originalName` metadata up to 255 characters; HEIC is let through so `photos.onUpload` can refuse it with `apiError.photo.heicUnsupported`), and `uploads/rasters/...` (TIFF; under 8 GiB, ids of `ID_PATTERN`); only admins read; everything else is written by service accounts only. **No SVG, ever.** The public bucket is written only by service accounts. A photo upload makes two Firestore lookups from the Storage rules (the admin document and the photo document); if production allows only one, drop the photo-document check.
- Storage counts **overwriting an existing object as `create`**: upload rules require `resource == null` (found by the rules tests).

## Rules tests (`firebase/rules-tests`, workspace `@hcm/rules-tests`)

- `@firebase/rules-unit-testing` (needs Node 24.12 or later, `firebase` 13) under the emulators: `npm test` = `firebase emulators:exec --project demo-hcm --only auth,firestore,storage 'bash scripts/ci/run-emulated-tests.sh'` (every Vitest project, one merged lcov). About 715 tests in 30 to 75 s.
- The emulators load the rules from `firebase.json` once: never pass `rules` to `initializeTestEnvironment` (a reload resets the coverage) and never clear data; test files run in parallel, so each owns a scope (persona uids and city ids prefixed with it). Personas live in `firebase/rules-tests/test/support/world.ts` (`anonymous`, `stranger`, `invited`, `unverified`, `otherProvider`, `revoked` = claim without document, `pending` = document without claim, `admin`), with **one cached context per persona** (a context per request made the suite three times slower); complete, schema-valid fixtures in `firebase/rules-tests/test/support/documents.ts`.
- The files: `matrix.test.ts` (every persona × collection × get, list, create, update, delete), `client-writes.test.ts` (each `CLIENT_WRITES` field allowed, each other schema field refused, read back through zod), `documents.test.ts` (the fixtures are complete and valid), `limits.test.ts` (the expression budget of the heaviest writes), `indexes.test.ts`, `history.test.ts` (`@S-A23-BAD-CLIENT-WRITE` for each audited entity), `pois.test.ts`, `identity.test.ts`, `cities.test.ts`, `photos.test.ts`, `layers.test.ts`, `jobs.test.ts`, `storage.test.ts`, `firebase-config.test.ts` (emulator ports, `.firebaserc`, the Hosting site and headers).
- **Rule coverage** (`scripts/ci/check_rules_coverage.py`, the `rules-coverage` gate of the tests stage): `save` fetches the emulator's rule-coverage report inside `emulators:exec`; `check` fails when an expression was never evaluated, an `allow` never allowed or never denied a request, or the report is stale. Storage has no coverage report, so each Storage `allow` gets its happy and bad row instead.

## Emulators

- firebase-tools 15.33.0 (root dev dependency) on JDK 21 (firebase-tools 15 refuses older Java). The Firestore, Storage and Pub/Sub emulator JARs are baked into the quality image at `/opt/hcm/firebase-emulators` (`FIREBASE_EMULATORS_PATH`), so tests need no download. Ports (`firebase.json`): hub 4400, logging 4500, auth 9099, Firestore 8080 (WebSocket 9150), Storage 9199, Functions 5001, Hosting 5000, Pub/Sub 8085, Cloud Tasks 9499; no UI.
- Always inside the quality image (Docker-only rule): `firebase emulators:exec --project demo-hcm --only <list> "<command>"`. The unit tiers use `auth,firestore,storage`; the Functions emulator with `functions,firestore,auth,storage,pubsub,tasks` loads every function from `functions/dist/` (`ops.tick` and `ops.onBudget` need Pub/Sub, `publish.buildManifest` its Cloud Tasks queue).
- The Firestore emulator refuses descending scans on the document id (`FAILED_PRECONDITION: Firestore does not support descending key scans`); the Storage emulator ignores `ifGenerationMatch` (the conflict mapping is unit-tested instead).
- e2e topology (M2b, `docs/research/M2b-interfaces.md` §6.2): emulators for auth, firestore, storage, functions, pubsub and tasks; functions run from `functions/dist/` with `HCM_UPSTREAM_BASE` pointing at the mock APIs, whose fake upstreams answer Google, Mapbox and USGS (`docs/TESTING.md` → *Emulators*). The admin's `e2e` build is served under `/admin/` of the e2e Hosting server (`e2e/mock-apis/admin-server.ts`, the e2e build's Hosting tree as `firebase.json`'s rules resolve it, M6), not by the Hosting emulator, whose `firebase.json` CSP carries `upgrade-insecure-requests` and would upgrade the http emulator calls. `setup/owner`, `setup/status` and `admins/*` are per project, so the admin tier runs in one worker from emptied emulators. Secrets live in the fake Secret Manager of the mock APIs (each function runs in its own worker process, so memory is not shared); nothing secret is configured for it. The emulator cannot run a v2 scheduled function from its Pub/Sub topic (its signature is `http`): the e2e world posts to `ops.tick`'s trigger route instead (`EmulatorWorld.runOpsTick`). Restart the emulators after rebuilding `functions/dist`.
- Isolation: each test namespaces data by city id `e2e-w{workerIndex}-{testId}` and unique Auth users; seeding goes through the Admin SDK pointed at the emulators (`@hcm/test-support`).
- The admin connects to the emulators only when built with the `e2e` mode; that branch is unit-tested too.

## Rules the M2c integration taught (`docs/LESSONS.md` 77, 78, 149)

- A collection-group rule (`match /{path=**}/history/{entry}`, History's recent changes) matches every collection of that name in the database. A condition on the path (`path[0] == 'cities'`) cannot hold for a collection-group query (the emulator denies the whole query), so it can narrow `get` only: `allow list: if isAdmin(); allow get: if isAdmin() && path[0] == 'cities';` (`docs/research/DECISIONS-for-review.md` §35c). The default-deny matrix (`firebase/rules-tests/test/identity.test.ts`) is what catches a recursive wildcard that opened too much.
- A collection-group query is kept to its owner on the server: the documents carry the owner's id (`cityId` on every history entry), the query asks `cityId ==` first and the composite indexes start with it (`firebase/rules-tests/test/indexes.test.ts`). Filtering other owners' documents out in the page lets them decide which of the owner's documents make the page's limit, and change it while a test looks (lesson 149).
- A new server-owned field of a schema needs a value in the rules tests' complete document (`firebase/rules-tests/test/support/documents.ts`), or the generated "a client cannot change or remove it" tests pass for nothing and the create test sends `undefined`.

## Agent rules

- The user logs in to Firebase themselves (`npx -y firebase-tools@15.33.0 login` in their own terminal). Agents never run `login:ci`, create tokens or keys, or type credentials.
- `firebase deploy` and any `firebase` / MCP action that changes a project are **ask first**, per action.
- Firebase logs (`firebase-debug.log`, `firestore-debug.log`, `pubsub-debug.log`, `ui-debug.log`, `.firebase/`) are git-ignored.
